# Telegram control bot

The optional `wallapop-track telegram-bot` process provides deterministic Telegram
commands for Wallapop searches. It uses the same search repository and tracking
runner as the CLI; it does not contain a second tracking implementation.

## Setup

Set `WALLAPOP_TELEGRAM_BOT_TOKEN` and run migrations, then start:

```text
wallapop-track telegram-bot --poll-timeout 30 --log-level INFO
```

The process uses long polling, retries transient API failures, and exits cleanly
on SIGINT/SIGTERM. It does not require `WALLAPOP_TELEGRAM_CHAT_ID` for control
bot ownership. That variable remains supported for global/manual alerts.

## Commands

`/start`, `/help`, `/searches`, `/search_add QUERY [--min-price N] [--max-price N]`
and `/search_show ID` are supported, together with `/search_update ID --max-price N`,
`/search_enable ID`,
`/search_disable ID`, `/search_delete ID confirm`, and `/search_run ID`.

The first iteration supports price, include/exclude, title and description
include/exclude, brand, condition, category ID, and interval seconds filters.
Updates are partial: omitted fields and stored filters are preserved.
Telegram chat ownership is stored in `telegram_chats` and
`telegram_search_owners`; the canonical identity is the numeric `chat_id`, not a
username. Every read and write resolves the search through that association.

Deletion is protected by the explicit `confirm` suffix. In this iteration the
association is removed and the underlying search is deleted because searches are
not shareable yet. A future sharing model should only remove the association.

Notifications generated by an owned search are routed to its owner chat while
retaining the configured global Telegram destination for legacy/manual alerts.
Delivery idempotency and retry records remain unchanged.

The command parser produces `TelegramIntent`. A future LLM parser may translate
natural language into the same intent, but must still call `TelegramControlService`
and must never access SQL or repositories directly.
